# Команда GoDeck

Четыре переиспользуемые роли Codex, привязанные к этому репозиторию:

| Имя | Ответственность | Изменяет код |
| --- | --- | --- |
| `analyst` | Текущий E2E-путь, границы MVP, контракт, критерии приёмки | Нет |
| `frontend_developer` | React/Next.js, UI-состояния, интеграция с API, назначенные UI-тесты | Да, в выделенной зоне |
| `backend_developer` | Java/Spring, API, данные, AI-интеграция, backend-тесты | Да, в выделенной зоне |
| `reviewer` | Независимая проверка diff, сценариев, безопасности и тестов | Нет |

## Какие файлы за что отвечают

- `*.toml` в этой папке — определения custom agents. В каждом заданы `name`, `description` и `developer_instructions`.
- Инструкции роли находятся непосредственно в `developer_instructions`; отдельных копий в Markdown нет, чтобы они не расходились.
- Корневой `AGENTS.md` и вложенные `AGENTS.md` — общие правила соответствующей части проекта. Они не создают роли сами по себе.
- Этот README — инструкция для человека и координатора, а не пятая роль.

Модели, reasoning effort и разрешения здесь не переопределены. Роли используют настройки родительской сессии с учётом настроек Codex. Указание «не менять код» — инструкция роли, а не отдельная read-only защита файловой системы. Глобальные настройки Codex не изменяются.

## Как запускать

Попроси Codex использовать роли по имени. Например:

> Реализуй загрузку PDF и DOCX с командой sub-agents: analyst, frontend_developer, backend_developer и reviewer. Сначала аналитик должен исследовать текущий путь и предложить MVP и API-контракт. После согласования контракта распредели реализацию между frontend и backend, затем выполни независимое ревью и итоговую проверку. Не расширяй задачу на импорт корпоративных шаблонов.

Это пример будущего поручения: создание профилей само по себе не запускает реализацию загрузки файлов.

Для отдельной проверки достаточно:

> Поручи reviewer проверить текущие изменения относительно main, включая незакоммиченные файлы. Код пока не исправляй.

Если новая роль не обнаружена текущим клиентом, начни новую сессию в этом репозитории и повтори запрос. В текущем чате можно явно поручить sub-agent прочитать нужный TOML и следовать его `developer_instructions`; это явная передача инструкций, не подтверждение автоматического обнаружения профиля.

## Порядок работы

1. Основной агент остаётся координатором: фиксирует запрос, ограничения и критерии завершения. Запускает роли, когда пользователь просит делегирование; для короткого вопроса вся команда не нужна.
2. `analyst` исследует текущий код и возвращает план, критерии приёмки и предлагаемый контракт. Необходимые пользовательские решения нельзя заменять догадкой.
3. Координатор согласует контракт и раздаёт разработчикам непересекающиеся файлы. Frontend и backend работают параллельно только там, где зависимости уже определены.
4. В одной рабочей папке агенты видят изменения друг друга. Общие `e2e/`, `scripts/`, настройки и зависимости имеют одного назначенного владельца. Отдельные worktrees автоматически не создаются.
5. `reviewer` проверяет законченный diff после завершения разработчиков. Findings возвращаются координатору и владельцу исправления; reviewer сам код не меняет.
6. Координатор сверяет результат с критериями, организует исправления и выполняет общую проверку. Полные тесты, сборка и E2E не запускаются одновременно несколькими агентами.
7. Пользователь получает сводку: что изменено, что проверено, что не проверено и какие риски остались. Commit/push/MR/deploy выполняются только по отдельному поручению.

Количество ролей не означает, что четыре sub-agent должны работать одновременно. Аналитик нужен перед реализацией, reviewer — после неё; фактическая параллельность ограничивается текущей сессией Codex. Дополнительные агенты расходуют дополнительные токены.

## Проверки проекта

Команды запускаются из корня репозитория; выбирай относящиеся к изменению проверки:

- Frontend: `pnpm typecheck`, `pnpm test:frontend`.
- Типы E2E: `pnpm test:e2e:types`.
- Backend: `pnpm backend:test:unit`, `pnpm backend:test:integration`.
- Сквозные сценарии: `pnpm test:e2e`; локальная инфраструктура — `pnpm infra:up`.
- Полная проверка перед передачей существенного изменения: `pnpm verify`.
- Для изменений авторизации — также локальный HTTP smoke согласно корневому `AGENTS.md`.

Не обещай успешный прогон, если команды не запускались. Моки проверяют контракт и обработку сценария, но не заменяют проверку настоящего провайдера и качества его ответа.
