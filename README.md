# GoDeck

Один репозиторий, два отдельных приложения:

```text
frontend/       Next.js: сайт, шаблоны, авторизация и кабинет
backend/        Java 26 + Spring Boot 4.1.1: API авторизации
scripts/        Запуск и проверки, мост v0 → GitLab
docs/           Документация
compose.yaml    Локальные PostgreSQL и Mailpit
```

## Локальный запуск

Нужны Node.js 22+, pnpm 10.10.0, JDK 26 и Docker. Maven устанавливается wrapper-скриптом; системный Maven не нужен. Скрипт бэкенда также распознаёт ранее скачанный JDK в `.tools/jdk-26.0.2.1+1/Contents/Home`.

Из корня проекта:

```sh
pnpm install --frozen-lockfile
pnpm infra:up
```

В одном терминале запустите API:

```sh
pnpm backend:dev
```

В другом — интерфейс:

```sh
pnpm dev
```

- Интерфейс: http://localhost:3000/auth
- API: http://127.0.0.1:8081/api/auth/csrf
- Локальные письма: http://localhost:8025
- PostgreSQL: `127.0.0.1:5433`, база и пользователь `godeck`, пароль `godeck-local-only` (только локальная разработка).

Письма не уходят наружу: SMTP слушает Mailpit на `127.0.0.1:1025`. Подтверждение регистрации и восстановление пароля проверяются через его интерфейс. `pnpm infra:down` останавливает контейнеры, сохраняя данные.

Если порт 3000 занят, задайте одинаковый адрес для API и проверки:

```sh
# Терминал API
FRONTEND_URL=http://localhost:3001 pnpm backend:dev
# Терминал интерфейса
pnpm dev --port 3001
# После запуска обоих приложений
AUTH_BASE_URL=http://localhost:3001 pnpm test:auth
```

`frontend/.env.example` содержит настройку `BACKEND_URL`. При необходимости скопируйте его в `frontend/.env.local`. Java читает переменные окружения из терминала/настроек запуска IDE; список — в `backend/.env.example`. Файл `.env` сам по себе Spring Boot не загружает.

## Авторизация

Страница `/auth` использует настоящий API:

1. Email → пароль для существующего аккаунта или создание пароля для нового.
2. Регистрация отправляет шестизначный код на почту. Аккаунт создаётся после подтверждения.
3. После подтверждения или входа открывается `/account`, данные берутся из `/api/auth/me`.
4. Восстановление пароля отправляет одноразовую ссылку на `/auth/reset/`.

Пароли и коды хешируются BCrypt. Код действует 10 минут, лимит — 5 неверных попыток, повторная отправка доступна через 60 секунд. Ссылка восстановления действует 30 минут. Смена пароля завершает ранее выданные сессии.

Сессия хранится на сервере; браузер получает HttpOnly/SameSite cookie. POST-запросы защищены CSRF. Вход и подтверждение меняют идентификатор сессии. Встроены ограничения попыток входа и частоты запросов. Ответ восстановления одинаковый для существующей и неизвестной почты. Email-first шаг `/identify` по дизайну раскрывает наличие зарегистрированного email.

Подробности API, ограничения и восстановление исходников: [docs/authentication.md](docs/authentication.md).

## Проверки

```sh
pnpm typecheck
pnpm build
pnpm backend:test
pnpm test:bridge
pnpm test:auth
```

- `backend:test` требует PostgreSQL из Compose, использует отдельную схему `auth_test` и тестовую отправку писем.
- `test:auth` требует работающих фронтенда, API и Mailpit; проходит полный сценарий через Next.js proxy и реальные локальные письма. Создаёт один тестовый аккаунт и два письма, не запускается против внешних адресов.
- `STATIC_EXPORT=1 pnpm build` собирает статический сайт в `frontend/out/`.

## CI, публикация и v0

GitLab запускает проверки соответствующих частей проекта на ветках и merge requests. Для `main` после проверок выполняются публикация статического сайта на REG.RU и синхронизация `main` в GitHub. Настройки и секреты описаны в [docs/deployment.md](docs/deployment.md).

**Этот репозиторий пока не разворачивает Java API на REG.RU.** Для работающей авторизации на публичном сайте нужно отдельно запустить API с PostgreSQL/SMTP и проксировать `/api/*` на него. Статический экспорт не содержит Next.js proxy. Локально proxy уже настроен и включается при обычном `pnpm dev`/`pnpm start`.

v0 продолжает получать код через GitHub. Корневые `pnpm dev` и `pnpm build` перенаправляют команды в `frontend`, поэтому локальный запуск из корня сохраняется. При импорте нового monorepo-проекта выбирайте `frontend` как Root Directory. Для существующего проекта **Vercel Root Directory нужно сменить на `frontend` при переходе на эту ветку**, иначе старые настройки будут искать приложение в корне. `frontend/vercel.json` задаёт команды Next.js. `BACKEND_URL` на Vercel должен указывать на доступный оттуда Java API; локальный API из облака недоступен.

Правки v0 делайте внутри `frontend/`. Старые чаты со своей веткой не получают перемещение автоматически: создайте новый чат от обновлённого `main` после слияния рефакторинга. Мост по-прежнему создаёт MR в GitLab; слияние выполняется там.
