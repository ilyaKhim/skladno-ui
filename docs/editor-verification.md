# Проверка и отладка редактора

Цель — защитить четыре основных пользовательских процесса перед выпуском MVP. Тесты работают с настоящими Next.js, Java API, PostgreSQL, загрузкой изображений и экспортом Apache POI. Ответы приложения не подменяются.

## Одна команда перед выпуском

Первоначальная настройка:

```sh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium webkit
pnpm infra:up
```

Нужны Node.js 22.18+ (или 24+), pnpm 10.10.0, JDK 26 и Docker для локального PostgreSQL. Проектный JDK в `.tools/` подхватывается автоматически.

```sh
pnpm verify
```

Команда последовательно проверяет frontend-тесты, TypeScript приложения и E2E, backend unit/integration tests, production-сборку Next.js, четыре основных browser-сценария и защитные сценарии RG-1–RG-3 в Chromium и WebKit.

### Windows

Используйте ту же команду `pnpm verify` в PowerShell или cmd. ОС определяется автоматически
через `process.platform`: `scripts/backend-dev.cjs` и `scripts/document-worker.cjs` на Windows
вызывают `backend/mvnw.cmd` через PowerShell, а на macOS/Linux делегируют существующим `.sh`.
Внутренние команды Playwright используют те же обёртки. Запускатор E2E на Windows вызывает
JavaScript-entrypoint pnpm через Node (или standalone `pnpm.exe`), не пытаясь выполнить
`pnpm.cmd` как обычный исполняемый файл и не передавая regex-фильтры тестов в shell.

Нужны JDK 26 (`JAVA_HOME`), Node.js 22.18+/24+, pnpm, Docker и браузеры Playwright. Если
`JAVA_HOME` не задан либо не содержит `bin/javac.exe`, обёртки ищут JDK с `26` в имени
под `%USERPROFILE%\.jdks`. Автоматического скачивания JDK нет. Если подходящего JDK IntelliJ
нет, действует обычное окружение Maven; установите JDK 26 и настройте `JAVA_HOME`/PATH.

Установка обёрток не создаёт screenshot-эталоны Windows. Сейчас в репозитории есть эталоны
macOS/Linux; Windows использует собственную папку `e2e/snapshots/win32/`. На Windows один раз
снимите эталоны, визуально проверьте и передайте их в Git:

```sh
pnpm test:e2e e2e/editor.spec.ts --grep "создать презентацию через студию" --update-snapshots=missing
```

Не копируйте Linux-изображения в `win32` и не отключайте сравнение: шрифты и сглаживание отличаются.
Для backend-тестов симлинков Windows также нужны соответствующие права (например, Developer Mode).
Это требования окружения, а не выбор другого launcher; обёртки их автоматически не меняют.

| Сценарий | Что проверяется |
| --- | --- |
| Создать и открыть | Вставить детерминированный ответ в студии, собрать PPTX, открыть редактор, загрузить настоящий фон, убедиться, что пять абзацев списка не пересекаются, сравнить screenshot |
| Изменить текст и положение | Изменить третий пункт, передвинуть общий text shape мышью, дождаться autosave, перезагрузить и проверить сохранённые текст и координаты |
| Добавить изображение | Загрузить PNG через UI, изменить описание, дождаться autosave, перезагрузить, проверить доступность изображения и его включение в экспорт |
| Экспортировать | Изменить текст и координаты, скрыть и переставить слайд, скачать PPTX, прочитать ZIP/XML, проверить абзацы, bullets, геометрию, отсутствие маркеров и новую версию |

## Редактирование на слайде и оформление текста

Двойной щелчок по тексту или Enter на выбранном блоке включает ввод непосредственно на слайде.
Enter внутри текста добавляет строку; Escape завершает ввод. Переключение на инструменты не закрывает
режим редактирования. Форматирование меняет весь PowerPoint text shape, включая его абзацы, а не
произвольный диапазон символов. Повторяющееся semantic field на другом слайде получает только текст,
но не оформление чужого блока.

Над canvas доступны шрифт, размер, жирный, курсив, подчёркивание, цвет и выравнивание. В отдельной
панели справа остаётся только AI-чат; на мобильном он открывается поверх рабочей области. Масштаб
50–150% позволяет редактировать текст без уменьшения до размера миниатюры. Геометрия по-прежнему
хранится в процентах независимо от масштаба.

`e2e/editor-formatting.spec.ts` проверяет ввод, фокус, переносы строк, клавиатурное форматирование,
undo/redo, сохранение и reload, фактические XML-атрибуты скачанного PPTX, responsive layout и масштаб.
Backend-тесты дополнительно защищают старые JSON без `text_style` и сохранение оформления при запросе
от старого клиента, который ещё не знает про новые поля.

Доступны Arial, Inter, Manrope, Georgia, Times New Roman и Courier New. Web-шрифты остаются локальными;
PPTX содержит имя шрифта, но не встраивает файл шрифта. Для одинакового вида в PowerPoint нужный шрифт
должен быть установлен на компьютере получателя. Это ограничение экспорта, не сетевой запрос к Google.

Дополнительно два сценария RG-1 задерживают ответ настоящего autosave дольше debounce. Во время
ожидания тесты вносят новые правки, вызывают ручное сохранение или экспорт и проверяют, что запросы
идут последовательно с обновлённой `draft_revision`, промежуточный текст пропускается, а последний
восстанавливается после reload и попадает в PPTX. Очередь держит только последний immutable snapshot.
При ошибке она останавливается без бесконечного retry. Дополнительные проверки RG-2/RG-3 воспроизводят
обрыв сети, validation error, настоящий конфликт двух вкладок, ошибку экспорта/перезагрузки документа,
быстрый выход, browser Back, refresh, закрытие и восстановление локальной копии.

Каждый запуск создаёт отдельную временную схему `editor_e2e_<random>` и отдельный каталог файлов. После остановки тестовых серверов они удаляются. Рабочие презентации и схемы `public`, `auth_test`, `generation_test` не очищаются. Тестовые серверы занимают `127.0.0.1:13000` и `127.0.0.1:18081`; существующий сервер на этих портах вызывает понятную ошибку вместо повторного использования.

В одной рабочей копии E2E запускается только последовательно: `.next-e2e` и артефакты Java общие,
даже если схемы БД различаются. До создания схемы и сборки запускатор занимает `.tools/e2e-run.lock`
и проверяет свободные порты. Второй запуск завершается до пересборки, не повреждая работающий
прогон. При обычном завершении или Ctrl+C lock снимается; он содержит PID владельца. После
принудительного завершения вроде `kill -9` lock может остаться: удалять именно этот файл можно
только после проверки отсутствия E2E-процессов и серверов на обоих портах. Чужой lock автоматически
не удаляется. `reuseExistingServer` не включайте: серверы относятся к схеме и AI-фикстуре своего запуска.

После каждого сценария удаляются только созданные им записи презентаций в изолированной схеме.
Это сохраняет независимость тестов при расширении suite; реальные лимиты генерации не отключаются.

На другой машине можно задать `E2E_DATABASE_URL` в формате `postgresql://user:password@host:port/database`. Учётная запись должна иметь право создавать и удалять схемы в тестовой БД. Эта переменная не влияет на рабочий `DATABASE_URL`.

## Посмотреть процесс по шагам

### Как найти вызов `/commit` во frontend

`/draft` и `/commit` решают разные задачи. Автосохранение записывает JSON черновика в БД; оно не
пересобирает PowerPoint. Экспорт сначала дожидается черновика, затем публикует его через `/commit`
как новую PPTX revision. Скачивание читает уже опубликованный файл.

| Действие | Цепочка вызовов | Запрос |
| --- | --- | --- |
| Изменить текст или расположение | `useEditorState.dispatch` → `autosave.update` → `save` в `EditorPageClient` → `generationApi.saveEditorDraft` | `PUT /editor/draft` |
| Нажать «Сохранить» или выйти в студию с правками | `editor.saveNow` → та же очередь → `save` | `PUT /editor/draft` |
| Нажать «Экспортировать» | `ExportMenu.startExport` → `EditorShell.exportDocument` → `editor.saveNow` → `EditorPageClient.exportPptx` → `generationApi.commitEditor` | Сначала `/draft`, затем `POST /editor/commit` и скачивание |

В React функцию передают дочернему компоненту через prop: `onExport={exportPptx}`. Это аналог передачи
ссылки на метод в Java, например `this::exportPptx`. Дочерний компонент позже вызывает `onExport()`.
Поэтому HTTP-запрос находится в `EditorPageClient`, хотя кнопку рисует `EditorToolbar`.

Файлы для чтения: `editor-toolbar.tsx` → `editor-shell.tsx` → `editor-page-client.tsx` →
`frontend/lib/generation-client.ts` → backend `PresentationEditorController.commit` →
`PresentationEditorService.commit`. Наличие этой цепочки проверяют E2E, которые скачивают и разбирают PPTX.

Демо-страница `/studio/editor-demo` — отдельная точка входа Next.js. У неё нет настоящего export callback,
поэтому она показывает прототип экспорта. Она не заменяет рабочий редактор `/studio/editor?presentation=...`.

### Запуск отладки

```sh
pnpm test:e2e:debug --project=chromium
```

Только один файл или сценарий:

```sh
pnpm test:e2e:debug e2e/editor-expanded-blocks.spec.ts --project=chromium
pnpm test:e2e:debug e2e/editor-expanded-blocks.spec.ts:11 --project=chromium
```

Алиас передаёт `--debug=inspector` явно: иначе Playwright может принять имя файла за режим `--debug`.

Откроется браузер и Playwright Inspector. Кнопками Step/Resume можно пройти клики, ввод, autosave и экспорт. В DevTools → Network видны настоящие запросы:

```mermaid
sequenceDiagram
    participant UI as React editor
    participant API as PresentationEditorController
    participant Draft as PresentationEditorService
    participant DB as PostgreSQL
    participant PPTX as PresentationTemplateService
    UI->>API: GET /editor
    API->>Draft: get(user, presentation)
    Draft->>DB: опубликованный content или draft
    Draft->>PPTX: editorDeck(template, content)
    PPTX-->>UI: shape, paragraphs, background_url
    UI->>API: PUT /editor/draft
    API->>Draft: save(user, snapshot)
    Draft->>DB: draft + optimistic revision
    UI->>API: POST /editor/commit
    Draft->>PPTX: render(content)
    Draft->>DB: новая revision + очистка draft
    UI->>API: GET download_url
    API-->>UI: PPTX
```

Для совместной отладки Java и браузера:

```sh
E2E_JAVA_DEBUG=1 pnpm test:e2e:debug --project=chromium
```

В IntelliJ создайте Remote JVM Debug с host `127.0.0.1`, port `15005`, Attach. Поставьте breakpoint в `PresentationEditorController.save`, `PresentationEditorService.save`, `PresentationTemplateService.editorDeck` или `PresentationTemplateService.render`. Это позволяет проследить одно действие от UI до сохранённой модели и PPTX. При длительной остановке Java сетевые ожидания теста могут истечь; после изучения продолжите или перезапустите выбранный сценарий.

## Ошибки и локальное восстановление

Ошибка открытия остаётся отдельным экраном. Ошибки save/export/reload показываются внутри работающего
редактора: введённый текст, выделение и undo history не размонтируются. Повтор сохранения и повтор
экспорта — отдельные действия. При `edit_expired` автоматические запросы блокируются до явного открытия
актуальной серверной версии: чужой черновик не перезаписывается автоматически.

`Открыть серверную версию` требует подтверждения и меняет документ только после успешного GET.
Неудачный запрос оставляет прежний документ и историю. Успешный экспорт обновляет только metadata
версий; он не сбрасывает undo history. Пока выполняется экспорт или переход, редактирование заблокировано,
чтобы новые изменения не попали между сохранением черновика и его публикацией.

Каждое изменение синхронно записывает резервную копию в `localStorage`. Ключ включает id вошедшего
пользователя, презентации и случайный id экземпляра редактора. Копии других вкладок не перетираются;
подтверждение save удаляет только собственную копию. Восстановленный снимок после успешного сохранения
помечается использованным. `Не восстанавливать` также скрывает только выбранный снимок. Запись другой
вкладки не удаляется: её новая правка остаётся доступной даже при одновременном обновлении. Пароли, коды и session credentials
в копию не попадают. Она содержит текст, композицию и ссылки на уже загруженные assets, а не байты изображений.

После повторного открытия копия предлагается в панели восстановления. Применение требует подтверждения:
оно заменяет документ и запускает autosave. Если опубликованная версия или контракт шаблона изменились,
автоматическое восстановление запрещено; JSON можно скачать для ручного переноса. Обычный конфликт
draft revisions также требует явного выбора пользователя. Локальные данные проверяются по schema version,
структуре и размеру; стили шаблона и URLs восстанавливаются из доверенного серверного документа.

Локальная копия ограничена 2 млн символов JSON. Если browser storage заблокирован или переполнен,
редактор остаётся рабочим, но показывает предупреждение и предлагает скачать JSON. Резервная копия
браузера не заменяет серверный backup; при очистке данных сайта она исчезнет.

Кнопка возврата в студию дожидается очереди сохранения. При ошибке переход не выполняется. Вход в редактор
использует обычную document navigation, чтобы browser Back проходил через `beforeunload`, а не обходил
его как переход Next.js SPA. Refresh и close используют системное предупреждение браузера при dirty state.
Оно требует пользовательского взаимодействия и может не сработать при аварийном завершении процесса;
поэтому локальная копия создаётся при изменении, а не только в обработчике выхода. При переходе вкладки
в фон копия обновляется. Обработчики выхода не начинают сетевые запросы: браузер не обязан их завершать.

## Разобрать падение

```sh
pnpm test:e2e:report
```

HTML-отчёт содержит шаг, на котором возникла ошибка. Для упавшего сценария сохраняются screenshot, видео и `trace.zip` в `test-results/`. Trace показывает DOM до/после действий, сетевые запросы и ответы. В GitLab эти файлы доступны в artifacts job `editor_e2e` в течение семи дней.

Чтобы записать trace успешного процесса и спокойно изучить его позже:

```sh
pnpm test:e2e --project=chromium --trace=on
```

```sh
pnpm exec playwright show-trace test-results/<scenario>/trace.zip
```

Эталонные screenshots находятся в `e2e/snapshots/{darwin,linux}/{chromium,webkit}/`.
macOS и Linux используют отдельные эталоны: сглаживание шрифтов отличается между ОС. Обновляйте
эталоны только после визуальной проверки ожидаемого изменения:

```sh
pnpm test:e2e --update-snapshots
```

Screenshot допускает небольшую разницу сглаживания внутри одной ОС; отсутствие перекрытия абзацев
проверяется отдельно по реальной DOM-геометрии. WebKit проверяет тот же движок, что используется Safari,
но не заменяет финальный короткий smoke test в установленном Safari. GitLab job использует официальный
Playwright Linux-образ, согласованный с версией в lockfile.
Для обновления Linux-эталонов набор системных шрифтов тоже должен совпадать с CI:
`fontconfig` и `fonts-dejavu-core`. Сам по себе Playwright-образ без этих пакетов даёт другой
fallback для отсутствующего в Linux шрифта Segoe UI, особенно в WebKit. Не повышайте
порог screenshot-проверки, чтобы скрыть такое отличие окружения.

## Почему появился настоящий фон

Раньше canvas выбирал только условный цвет `paper/navy`; фон и декоративные shapes из PPTX не передавались браузеру. Теперь `TemplateSlideBackgrounds` рисует статическое оформление исходного слайда через POI, предварительно убрав текстовые маркеры. PNG кешируется в памяти процесса, URL содержит hash шаблона. Canvas и миниатюры используют один и тот же фон; semantic fields остаются отдельными редактируемыми слоями.

Рендер фона не обращается к Google Fonts, OpenAI или LibreOffice. При недоступности PNG основной canvas показывает ошибку с повторной загрузкой. Font colors извлекаются из PPTX, чтобы светлый текст оставался читаемым на тёмном фоне. Масштаб шрифтов и paragraph spacing рассчитывается относительно ширины слайда 960 px.

На Linux серверу Java нужны `fontconfig` и установленные шрифты (например, пакет `fonts-dejavu-core`). Это локальные системные ресурсы: браузер и сборка не скачивают шрифты Google. Подготовка сервера описана в [deployment.md](deployment.md#фоны-слайдов-в-java-api).

Проверки не обещают полного совпадения всех метрик PowerPoint: шрифты шаблонов могут отсутствовать в браузере или на сервере, а сложные эффекты POI может рисовать иначе. Четыре сценария также не вызывают платный OpenAI API и не тестируют оплату. Перед выпуском используется [короткий checklist](release-checklist.md).
