# Генерация PPTX в Java backend

Студия находится на `/studio/`. Все API ниже находятся под `/api/generation`, требуют сессию пользователя (или локальный `AUTH_BYPASS`) и CSRF-токен для изменяющих запросов. Токен выдаёт `/api/auth/csrf`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /health/ready` | Доступность сервиса и настройка AI |
| `GET /v1/models` | Список разрешённых моделей и `default_model` |
| `GET /v1/templates` | Реально установленные PPTX-шаблоны |
| `GET /v1/templates/{templateId}/context` | Поля, лимиты текста и привязка полей к слайдам |
| `POST /v1/prompts/preview` | Подготовленный JSON для Responses API; не вызывает OpenAI и не создаёт задачу |
| `GET /v1/presentations` | История пользователя с пагинацией `limit`, `offset` |
| `POST /v1/presentations` | Создание проекта: `template_id`, `topic`, `mode` (`openai` или `manual`), необязательный `model` |
| `GET /v1/presentations/{id}` | Статус проекта и URL скачивания |
| `PUT /v1/presentations/{id}/content` | Поля и решения о включении всех слайдов для ручного проекта |
| `POST /v1/presentations/{id}/cancel` | Отмена проекта, ожидающего материалов или находящегося в очереди |
| `GET /v1/presentations/{id}/download` | Текущий PPTX пользователя |
| `GET /v1/presentations/{id}/versions/{version}/download` | PPTX конкретной сохранённой версии; только владельцу |
| `POST /v1/presentations/{id}/chat` | Правка: `{"message":"Сократи введение"}` |
| `GET /v1/presentations/{id}/versions` | Сохранённая история версий и запросов |
| `GET /v1/presentations/{id}/ai-calls` | Фактические запросы и исходные ответы OpenAI; только владельцу, `Cache-Control: no-store` |

`POST /v1/presentations` поддерживает заголовок `Idempotency-Key` (8–100 латинских букв, цифр, `_`, `-`). Повтор запроса с тем же ключом возвращает существующий проект; изменение темы, шаблона или режима с прежним ключом возвращает 409. Лимит пользователя: 10 новых проектов в сутки и 3 незавершённых одновременно. Чат допускает 30 успешных правок в сутки.

Студия получает список моделей с сервера: GPT-6.1 Sol, GPT-6 Luna, GPT-6 Astra, GPT-5.6 Sol, GPT-5.6 Terra, GPT-5.6 Luna, GPT-5.4 и GPT-5.4 Mini. Если `OPENAI_MODEL` задаёт другую модель по умолчанию, сервер также добавляет её в список. `model` принимают создание проекта, просмотр запроса и чат; неизвестная модель возвращает 422 до вызова OpenAI. Выбор сохраняется с проектом и учитывается в `Idempotency-Key`. Очередь использует сохранённую модель, даже если выбор в интерфейсе уже изменился. Чат использует модель проекта, пока пользователь не выберет другую для правки; в истории версий сохраняется модель каждой AI-операции. Ручная сборка не вызывает модель.

## Сборка готового ответа LLM

На вкладке «Создание» выберите шаблон, способ «Вставить ответ LLM» и вставьте полный JSON-ответ OpenAI в одно поле. Поддерживаются Responses API (`output[].content[].text` или `output_text`), Chat Completions (`choices[0].message.content`), а также непосредственно JSON с `fields` и `slides`, в том числе в блоке кода JSON. Оболочка API остаётся в браузере; на сервер отправляется только содержимое презентации. После отправки открывается вкладка «Недавние» со статусом проекта. Текст ответа сохраняется при переключении вкладок и способов создания.

JSON рядом с PPTX используется как описание шаблона в запросах генерации, просмотра запроса и чат-редактирования. `field_hints.*.max_chars` задаёт лимиты текста; стиль, подсказки и назначение макетов передаются модели. Выбор слайдов при сборке определяется ответом LLM (`include`); пустые поля не приводят к автоматическому исключению макета.

Используется существующий режим API `manual`, без обращения к OpenAI. Проект создаётся со статусом `awaiting_content`; затем клиент отправляет объект:

```json
{
  "fields": { "TITLE": "Заголовок", "AUTHOR": "Имя", "...": "остальные поля контекста" },
  "slides": [
    { "slide": 1, "include": true, "reason": "Выбрано пользователем" },
    { "slide": 2, "include": false, "reason": "Выбрано пользователем" }
  ]
}
```

Нужно передать все поля и по одному решению для каждого слайда шаблона. Номера слайдов должны быть целыми, уникальными и входить в диапазон шаблона. Хотя бы один слайд должен быть включён. Поля исключённых слайдов можно оставить пустыми. Длинный текст обрезается по лимиту соответствующего поля; сохранённый план содержит значения, которые попали в PPTX.

После отправки проект проходит `queued` → `running` → `succeeded` или `failed`. Очередь хранится в PostgreSQL; её обрабатывает планировщик Spring. Задача, оставшаяся в `running` дольше пяти минут, помечается ошибкой `worker_interrupted`.

## Чат и версии

Чат доступен для готовой презентации, чей план сохранён в базе. Запрос синхронный: сервер передаёт текущий план и просьбу пользователя в OpenAI, проверяет ответ и создаёт новый PPTX. Соединение имеет таймаут 10 секунд, чтение ответа — 2 минуты. Для этой функции при развёртывании нужно учитывать таймаут HTTP-прокси.

На вкладке «Недавние» кнопка «История версий» показывает все сохранённые версии презентации. У каждой есть отдельная кнопка скачивания; текущая версия отмечена. API списка версий возвращает `download_url` для каждой записи; файл скачивается с номером версии в имени (`godeck-<id>-v<номер>.pptx`). Скачивание старой версии не меняет текущую. Если файл был удалён с диска или версия не существует, сервер возвращает 404.

Правки одной презентации сериализованы меткой активной правки в PostgreSQL: параллельный запрос получает 409 `edit_in_progress` до вызова модели. Короткая транзакция резервирует правку; вызов AI и сборка PPTX выполняются без открытой транзакции БД. Вторая короткая транзакция проверяет токен правки и атомарно сохраняет версию, содержимое и указатель на файл. При ошибке метка снимается; после аварийного завершения она может быть заменена через пять минут. Устаревший результат не перезапишет новую правку. Каждый результат получает отдельное имя файла; неудачная правка сохраняет предыдущую успешную версию.

Файлы сохраняются на постоянном диске в `GODECK_DATA_DIR` (по умолчанию `backend/data/presentations/` при запуске через скрипт). Для нескольких экземпляров API нужен общий каталог с файлами. Миграции Flyway создают таблицы проектов и версий и применяются при запуске backend.

## История обращений к AI

На вкладке «Недавние» в каждой карточке есть раскрываемый блок «Запросы к AI». Для генерации и каждой чат-правки сохраняются модель, операция, время начала, длительность, HTTP-статус, тело отправленного запроса, исходное тело ответа OpenAI и код ошибки. Запрос и ответ можно раскрыть и скопировать отдельно. Во время выполнения открытый блок обновляется автоматически; после неудачной правки история также обновляется.

История хранится в PostgreSQL (`presentation_ai_calls`, миграция V7), остаётся после перезапуска и доступна только владельцу презентации. Запись запроса создаётся перед HTTP-вызовом; завершение сохраняется отдельной короткой транзакцией. Неполный ответ, некорректный JSON и HTTP-ошибка остаются в истории. Если соединение не дало ответа, тело ответа и HTTP-статус отсутствуют. После аварийного завершения процесса может остаться запись без завершения — это видно как «Ответ ещё не записан».

В обычные логи backend попадают ID обращения и презентации, операция, модель, HTTP-статус, длительность и код ошибки. Полные тела хранятся в БД; заголовок Authorization не сохраняется, значение настроенного API-ключа маскируется в телах. Тексты запросов и ответов содержат материалы презентации, поэтому резервные копии этой таблицы также содержат эти материалы. Автоматического удаления истории сейчас нет; удаление презентации в БД каскадно удаляет её обращения.

При отказе записи завершения диагностики backend журналирует ID обращения и тип ошибки и продолжает обработку полученного плана. Такая запись может остаться со статусом «Ответ ещё не записан». Если невозможно сохранить начало обращения, запрос в OpenAI не отправляется.

Сборка из вставленного ответа LLM и предварительный просмотр не отправляют запрос в OpenAI и не создают запись обращения. История появляется только у новых вызовов; ранее сделанные обращения восстановить нельзя. Успешный ответ в этой истории означает получение и разбор плана от AI; последующая проверка шаблона или сборка PPTX может завершиться отдельно с ошибкой.

## Конфигурация

- `AUTH_BYPASS=false` — обычная авторизация. `pnpm backend:dev` включает bypass по умолчанию, только при loopback-адресе Java-сервера.
- `OPENAI_API_KEY` и `GODECK_OPENAI_ENABLED=true` — вызовы OpenAI; по умолчанию выключены.
- `OPENAI_MODEL` — модель Responses API, по умолчанию `gpt-6.1-sol`.
- `GODECK_DATA_DIR` — каталог выходных PPTX.

Ключ API остаётся в окружении backend и не включается в предварительный просмотр запроса. Публичный статический фронтенд требует отдельного развёртывания Java API и проксирования `/api/*`, как описано в основном README.

Для локального запуска эти переменные можно задать в `backend/.env.local` в формате `KEY=value`. Spring Boot импортирует файл при рабочем каталоге в корне проекта или `backend/`; переменные окружения имеют приоритет. Файл исключён из Git. В `application.yaml` остаётся ссылка `${OPENAI_API_KEY:}`.
