# Материалы: API и отдельный document-worker

Пользователь загружает один PDF/DOCX/TXT, проверяет и исправляет извлечённый текст, задаёт тему и создаёт черновик презентации. Только создание презентации отправляет подтверждённые материалы AI. Само извлечение текста AI не вызывает.

## Границы двух Java-программ

- `backend/`: сессии, владельцы, проверка загрузки, очередь `material_jobs`, презентации, AI, редактор и версии.
- `document-worker/`: отдельный обычный Java `main`, JDBC и парсеры PDFBox/POI. Нет Spring-контекста, HTTP, пользовательских сессий и доступа к AI. Он не зависит от backend-артефакта.

API принимает файл до 5 МиБ и атомарно сохраняет задание в PostgreSQL, возвращая `202`. Worker захватывает задание через `FOR UPDATE SKIP LOCKED`, разбирает ограниченный массив байтов и записывает результат. Промежуточных файлов, дочерних процессов внутри API и временного JSON нет. Frontend опрашивает API; при reload может продолжить по непрозрачному ID в sessionStorage — сам текст и исходник туда не записываются.

## API

- `POST /api/generation/v1/materials/extract`, multipart `file` → `202 {id,status,result,error}`.
- `GET /api/generation/v1/materials/{id}` → `200` с тем же объектом, только для владельца; чужой/истёкший ID → `404`.
- Статусы: `queued`, `running`, `succeeded`, `failed`. У успешного задания `result` содержит `format,name,text,characters,pages,warnings`. У неуспешного `error` содержит публичные `code,message`.
- Неправильный формат/размер отклоняется сразу. Ошибки парсера становятся `failed` в результате задания, а не HTTP-ошибкой чтения статуса. Сессия, CSRF для POST и `no-store` сохранены.
- Создание презентации принимает прежние `goal,audience,source:{format,name,text}`; передаётся исправленный пользователем текст. Worker презентаций использует сохранённый снимок и не зависит от вкладки браузера.

## Ограничения и восстановление

Один файл до 5 МиБ; PDF до 20 страниц и только с текстовым слоем; DOCX — основной текст и простые таблицы; TXT — UTF-8. Не больше 30 000 символов. OCR, оформление, вложения и распознавание графиков не поддерживаются. Неполный PDF требует подтверждения; полностью пустой отклоняется. Превышение лимита не обрезает содержимое молча.

Очередь ограничена 20 активными заданиями в целом и двумя на пользователя. Задание ожидает worker не более 60 секунд. Один worker обрабатывает один документ; claim действует 10 секунд. Жёсткий watchdog завершает JVM через 5 секунд обработки, даже если парсер игнорирует interrupt. Локальный supervisor или Docker перезапускает worker; API продолжает работу. Такое задание получает ошибку по истечении claim, не бесконечные скрытые повторы. Токен и deadline не позволяют старому результату переписать новое состояние.

Бинарник удаляется из строки атомарно с завершением/ошибкой. API также очищает просроченные задания при опросе/приёме и каждую минуту; результаты и брошенные задания живут не более часа плюс задержка периодической очистки. Исходник может присутствовать в резервных копиях/WAL БД — их срок хранения нужно настраивать отдельно.

Контекст уже созданной презентации живёт отдельно: очищается через 30 дней после публикации/ошибки/отмены, не удаляя факты из слайдов. Личная история AI-вызовов сохраняет реальные тела запросов и ответов, включая переданные материалы, с маскированием API-ключа. Она доступна только владельцу презентации; общий журнал сервера содержит только метаданные вызова. Очистка исходного контекста не удаляет его копию в истории AI-вызовов.

## Запуск

После `pnpm infra:up` запустите API (`pnpm backend:dev`), worker (`pnpm document-worker:dev`) и frontend (`pnpm dev`) в отдельных терминалах. В IDEA импортируйте `document-worker/pom.xml` как Maven-проект и запускайте `ru.godeck.documents.DocumentWorker`.

Worker читает только `DATABASE_URL` (JDBC URL, включая `currentSchema` при необходимости), `DATABASE_USER`, `DATABASE_PASSWORD`. Локальные значения по умолчанию совпадают с compose. В отличие от Spring API, он **не читает** `backend/.env.local`: нестандартные настройки передаются окружением. Не передавайте ему OpenAI/SMTP-ключи.

Альтернатива: `docker compose --profile documents up -d --build document-worker` после применения миграций API. Контейнеру заданы лимиты 256 МиБ/1 CPU, read-only filesystem и временный `/tmp`. В production создайте отдельную роль БД worker: только `USAGE` нужной схемы и `SELECT,UPDATE` таблицы `material_jobs`; не права на пользователей, презентации или AI-аудит. Локальные compose credentials для production не использовать.

## Проверки

`pnpm document-worker:test` проверяет парсеры в их модуле. `pnpm backend:test` — очередь, владельцев, CSRF, валидацию, expiry и очистку. `pnpm test:e2e` собирает и запускает настоящий worker/API/БД на изолированной схеме и проверяет три формата до PPTX, reload обработки и ошибки. Только AI заменён локальным HTTP-ответом, платных запросов нет. Docker-артефакт проверяется отдельно от локального Java-запуска.
